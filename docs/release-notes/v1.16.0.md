# v1.16.0 release notes

These notes describe the v1.16.0 feature set. Check the [GitHub releases page](https://github.com/Holden-Lin/claudex-switch/releases) for current availability.

- OpenCode V2 profiles: a managed V2 run starts OpenCode with `--standalone` and gives each alias its own XDG data / state / cache roots and SQLite database, overriding any inherited `OPENCODE_DB`. V2 history and credentials stay within each alias; normal / native OpenCode history and other aliases are not imported, and a managed launch does not modify OpenCode's normal default store.
- V2 credentials: `add` / `refresh` prompt for the Go API key with masked input, do not export it from OpenCode's SQLite database, and do not validate it against OpenCode Go up front; an invalid key may fail only on its first provider request. The key stays in the alias's private claudex-switch profile and is synced into the alias-private OpenCode credential store through the supported local integration API before each launch; the short-lived sync server binds to loopback only, and the key is not passed in argv or the child environment. A failed sync prevents launch. TUI `/connect` can change the session credential but does not rewrite the claudex sidecar; the next claudex launch resyncs it.
- V2 preflight: a managed launch rejects a positional directory, `--continue` / `--session`, and unknown forwarded arguments, and checks the effective Go model, default agent, and model inventory in the launch working directory; a non-Go default-agent model, an unavailable Go model, or another provider in the inventory fails closed. The current agent's permission / system settings are not rewritten.
- V1 unchanged: V1 continues to import or `/connect` a private credential and inject it through `OPENCODE_AUTH_CONTENT` while sharing normal `/resume` history. All other providers are unchanged as well.
- CI: a new `opencode-v2-runtime` job runs the built product CLI against digest-pinned OpenCode v2.0.6 servers in a network-disabled container and checks launch config, credential sync / cleanup, alias A/B database separation, default-store sentinels, manual `/connect` reset, refreshed-sidecar use on the next launch, fail-closed policy / model cases, shutdown, and absence of fake keys in logs. The fixture intercepts the final TUI call; interactive TUI behavior, interactive add / refresh prompts, session navigation / resume, and live model requests remain unverified.
